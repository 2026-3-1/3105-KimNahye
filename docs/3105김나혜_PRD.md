```bash
# 1. PostgreSQL (Docker)

  -e POSTGRES_DB=solving-meal -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=1234 \

# 2. 서버
cd server
cp .env.example .env        # 아래 9.1 절 참고하여 값 채우기

npm run start:dev           # → http://localhost:8080, Swagger: /api/docs

# 3. 클라이언트
cd ../client
echo VITE_API_URL=http://localhost:8080/api/v1 > .env
npm install
npm run dev                 # → http://localhost:5173
```

검증 체크리스트:
- `GET http://localhost:8080/api/v1/courses/list` 가 `{ statusCode: 200, message, data: [] }` 를 반환한다.
- `http://localhost:5173` 에 접속하면 주황색(`#ffa500`) 테마의 "끼니해결" 홈 화면이 보인다.
- 회원가입(`teacher` 1명, `student` 1명) → 로그인 → 코스 생성 → 영상 등록 → 다른 계정으로 수강신청 → 영상 시청(이어보기·북마크·완료처리) → 리뷰 작성 흐름이 동작한다.

## 1. 제품 개요

### 1.1 비전
**Solving Meal**(브랜드: "한끼해결" / 네비바 표기 "끼니해결" / 로그인 화면 표기 "🍳 쿡클래스")은 자취생·요리 입문자를 위한 **인터랙티브 요리 교육 커리큘럼** 웹 서비스이다. YouTube 오픈 영상을 코스 단위로 묶어 카테고리·난이도·도구 조건으로 맞춤 학습할 수 있게 한다.

### 1.2 핵심 가치
| 가치 | 설명 |
| --- | --- |
| 커리큘럼 중심 | 단순 영상 나열이 아닌 코스 단위 체계 학습 |
| 자취생 맞춤 | 한식·일식·중식·양식·베이킹·반찬·일품요리 7개 카테고리 |
| YouTube 연동 | `youtubeVideoId` 기반, 자체 영상 호스팅 없음 (IFrame Player API 직접 사용) |
| 역할 분리 | STUDENT(학습) / TEACHER(코스 운영) / ADMIN(미사용) |
| 반응형 SPA | Vite + React 19, 모바일 360px ~ 데스크톱 1920px |

### 1.3 타깃 사용자
- **STUDENT**: 자취 초보, 혼밥족, 요리 입문 성인
- **TEACHER**: 요리 YouTube 채널 운영자, 요리 강사

## 4. 데이터 모델 (PostgreSQL + TypeORM)

전 엔티티 PK는 `PrimaryGeneratedColumn('uuid')`. timestamps: `@CreateDateColumn` / `@UpdateDateColumn`.

`AppModule` 설정:
```ts
TypeOrmModule.forRootAsync({
  inject: [ConfigService],
  useFactory: (config) => ({
    type: 'postgres',
    url: config.get('DATABASE_URL'),
    autoLoadEntities: true,
    synchronize: config.get('NODE_ENV') !== 'prod',  // 개발에선 자동 마이그레이션
    ssl: config.get('NODE_ENV') === 'prod' ? { rejectUnauthorized: false } : false,
  }),
})
```

### 4.1 `users`

| 컬럼 | 타입 | 제약 |
| --- | --- | --- |
| id | uuid | PK |
| email | varchar(255) | unique |
| password | varchar(255) | **`select: false`** (기본 조회에서 제외), `@BeforeInsert`로 bcrypt(rounds=10) 자동 해싱 |
| nickname | varchar(50) | not null |
| role | enum(`student`, `teacher`, `admin`) | default `student` |
| created_at, updated_at | timestamptz | 자동 |

관계: `OneToMany` → `refresh_tokens`, `videos`, `courses`, `enrollments`. 메서드: `validatePassword(plain)` (bcrypt.compare).

### 4.2 `refresh_tokens`

| 컬럼 | 타입 | 비고 |
| --- | --- | --- |
| id | uuid | PK |
| token | text | 발급된 refresh JWT 원문 그대로 |
| expires_at | timestamptz | |
| is_revoked | boolean | default `false` |
| user_id | uuid | FK → users, `onDelete: CASCADE`, `@Index` |
| created_at | timestamptz | |

메서드: `isExpired()`, `isValid()`. `userId` 컬럼이 별도로 노출되어 있어 `@ManyToOne` 외에 직접 쓸 수 있음.

### 4.3 `courses`

| 컬럼 | 타입 | 비고 |
| --- | --- | --- |
| id | uuid | PK |
| teacher_id | uuid | `ManyToOne User`, not null |
| category | enum(Category) | `@Column()` (타입 미지정 — DB는 enum 타입 자동 생성 시도, 실행 환경에 따라 varchar 가능) |
| difficulty | enum(Difficulty) | 동상 |
| requiredTools | jsonb | string 배열 — 예: `["knife","pan"]` |
| price | int | default `0` |
| createdAt, updatedAt | timestamptz | |

가상 getter:
- `computedVideoCount = this.videos?.length ?? 0`
- `computedTotalDuration = this.videos?.reduce((s,v)=>s+v.duration, 0) ?? 0`

**Category** = `KOREAN | JAPANESE | CHINESE | WESTERN | BAKING | SIDE_DISH | ONE_DISH`
**Difficulty** = `HIGH | MEDIUM | LOW`

```ts
{ provide: APP_PIPE,   useFactory: () => new ValidationPipe({
    whitelist: true, forbidNonWhitelisted: true, transform: true,
    transformOptions: { enableImplicitConversion: true },
  })
},
{ provide: APP_FILTER, useClass: AllExceptionFilter },   // catch-all 먼저
{ provide: APP_FILTER, useClass: HttpExceptionFilter },  // 구체적인 것 나중에 (Nest는 역순 적용 → HttpException 우선)
```

ValidationPipe 동작:
- `whitelist: true` — DTO에 없는 필드 자동 제거
- `forbidNonWhitelisted: true` — 허용 안 된 필드 들어오면 400
- `transform: true` + `enableImplicitConversion: true` — 쿼리스트링도 number/boolean 자동 변환

### 5.3 공통 응답 포맷 — `ApiResponseDto<T>`

```ts
class ApiResponseDto<T> {
  statusCode: number;
  message: string;
  data: T | null;
  static success<T>(data: T, message: string, statusCode: number): ApiResponseDto<T>;
  static error(message: string, statusCode: number): ApiResponseDto<null>;
}
```

모든 컨트롤러 메서드는 `return ApiResponseDto.success(data, '메시지', HttpStatus.XXX)` 로 응답한다.

### 5.4 전역 예외 필터 — `HttpExceptionFilter` / `AllExceptionFilter`

```ts
// HttpExceptionFilter
response.status(status).json({
  statusCode: status,
  message: Array.isArray(message) ? message[0] : message,  // class-validator 다중 메시지일 때 첫 번째만
  data: null,
});

// AllExceptionFilter (catch-all)
response.status(500).json({
  statusCode: 500,
  message: '서버 내부 오류가 발생했습니다.',
  data: null,
});
```

> ValidationPipe가 던지는 `BadRequestException`의 message 배열은 첫 번째 항목만 노출된다. 다국어/검증 메시지는 DTO 데코레이터의 `message:` 옵션으로 한국어로 작성.

### 5.5 인증 모듈

#### 5.5.1 토큰 정책
```ts
interface JwtPayload {
  sub: string;        // user UUID
  email: string;
  role: UserRole;
  type: 'access' | 'refresh';
}
```

| 항목 | Access | Refresh |
| --- | --- | --- |
| 만료 | `JWT_ACCESS_TOKEN_EXPIRES_IN` (기본 `1h`) | `JWT_REFRESH_TOKEN_EXPIRES_IN` (기본 `7d`) |
| 시크릿 | `JWT_SECRET_KEY` | `JWT_REFRESH_SECRET_KEY` |
| Strategy 이름 | `'jwt-access'` | `'jwt-refresh'` |
| Guard 클래스 | `JwtAccessGuard extends AuthGuard('jwt-access')` | `JwtRefreshGuard extends AuthGuard('jwt-refresh')` |
| 추출 위치 | `Authorization: Bearer <token>` 헤더 (공통) | 동일 — refresh도 Bearer 헤더로 전송 |
| 검증 | `payload.type === 'access'` 확인 → `UserService.findById(sub)` | `payload.type === 'refresh'` 확인 → 헤더에서 토큰 추출 → `RefreshTokenService.validate(userId, token)` |

`PassportModule.register({ defaultStrategy: 'jwt-access' })`.
`JwtModule.registerAsync` 기본 설정은 `secret: JWT_SECRET_KEY, signOptions.expiresIn: JWT_ACCESS_TOKEN_EXPIRES_IN ?? '1h'`. 실제 토큰 발급은 `TokenService.generateTokens(user)` 가 `signAsync({ ...payload, type:'access'/'refresh' }, { secret, expiresIn })` 를 명시적으로 사용.

#### 5.5.2 RTR (Refresh Token Rotation)
1. `/auth/login` → `tokens = { accessToken, refreshToken }` 생성 → `refresh_tokens` 테이블에 토큰 저장
2. `/auth/refresh` → `JwtRefreshGuard` → 기존 storedToken 검증 → 새 토큰 쌍 발급 → **기존 레코드 deleteOne → 새 레코드 저장**
3. `/auth/logout` → 해당 유저의 `refresh_tokens` 전체 삭제 (`deleteAll(userId)`)

### 6.1 인증 — `/auth`

| Method | Path | Auth | 성공 코드 | 메시지 |
| --- | --- | --- | --- | --- |
| POST | `/auth/register` | ✗ | 201 | `회원가입 성공` |
| POST | `/auth/login` | ✗ | 200 | `로그인 성공` |
| POST | `/auth/refresh` | ✓ Refresh | 200 | `토큰 재발급 성공` |
| POST | `/auth/logout` | ✓ Access | 200 | `로그아웃 성공` |

#### POST /auth/register
Request:
```json
{ "email": "user@example.com", "password": "password1234", "nickname": "닉네임", "role": "student" }
```
DTO 검증:
- `email`: `@IsEmail` — 메시지 `유효한 이메일 형식을 입력해주세요.`
- `password`: 8~20자, **영문+숫자 둘 다 포함** (`/^(?=.*[A-Za-z])(?=.*\d).+$/`)
  - 길이 미달: `비밀번호는 최소 8자 이상이어야 합니다.` / 초과: `비밀번호는 최대 20자 이하여야 합니다.`
  - 패턴 불일치: `비밀번호는 영문자와 숫자를 모두 포함해야 합니다.`
- `nickname`: 2~20자, `닉네임은 최소 2자 이상...` / `...최대 20자 이하여야 합니다.`
- `role`: `IsEnum(UserRole)` — `student | teacher | admin`. 미지원 값: `유효한 역할을 입력해주세요. (student, teacher, admin)`

Response 201:
```json
{ "statusCode": 201, "message": "회원가입 성공",
  "data": { "id": "uuid", "email": "...", "nickname": "...", "role": "student" } }
```

에러:
- **409** `이미 사용 중인 이메일입니다.` (이메일 중복)

#### POST /auth/login
Request:
```json
{ "email": "user@example.com", "password": "password1234" }
```
- `email`: `@IsEmail`
- `password`: 빈 문자열 금지 (`비밀번호를 입력해주세요.`)

Response 200:
```json
{ "statusCode": 200, "message": "로그인 성공",
  "data": { "accessToken": "eyJ...", "refreshToken": "eyJ..." } }
```

에러:
- **401** `이메일 또는 비밀번호가 올바르지 않습니다.` (이메일 미존재 또는 비밀번호 불일치 — 두 경우 모두 동일 메시지로 통일하여 사용자 열거 방지)

> 로그인 성공 후 서버는 `refresh_tokens` 테이블에 발급된 refresh token을 그대로 저장.

#### POST /auth/refresh
Header: `Authorization: Bearer <refreshToken>` (Bearer 헤더로 refresh token 전송)

Response 200: 신규 `{ accessToken, refreshToken }`. 기존 refresh token 레코드는 삭제(RTR).

에러:
- **401** `리프레시 토큰이 아닙니다.` / `리프레시 토큰이 없습니다.` / `존재하지 않는 사용자입니다.` / `유효하지 않은 리프레시 토큰입니다.`(RefreshTokenService 내부)

#### POST /auth/logout
Header: `Authorization: Bearer <accessToken>`

Response 200: `data: null`. 해당 유저의 `refresh_tokens` 전체 삭제.

### 7.3 Zustand AuthStore (`store/AuthStore.ts`)

```ts
type AuthState = {
  user: UserProfile | null
  accessToken: string | null
  isAuthenticated: boolean
  setAuth(user, accessToken, refreshToken): void   // refreshToken은 localStorage("refreshToken"), 나머지는 set
  setUser(user): void
  logout(): void   // localStorage 토큰 둘 다 제거 + 상태 초기화
}

create<AuthState>()(
  persist((set) => ({...}), { name: "auth-storage" })
)
```

`persist`가 `accessToken/isAuthenticated/user`를 `localStorage["auth-storage"]`에 직렬화. `refreshToken`은 **항상 `localStorage["refreshToken"]` 단독 키**에 저장 (Zustand 외부).

> 로그인 흐름: `Login.tsx`가 `login()` 응답에서 `{accessToken, refreshToken}`을 받아 `setAuth(null, access, refresh)` 호출 → `localStorage.setItem("refreshToken", ...)` 즉시 실행됨. **`accessToken`은 또한 `localStorage["accessToken"]`에도 따로 저장돼야 ApiClient 인터셉터가 사용 가능**(아래 7.4의 인터셉터가 `localStorage.getItem("accessToken")`을 읽음). 따라서 Login.tsx는 `apiClient.defaults.headers.common["Authorization"]`도 직접 설정하지만, **refresh 후 재요청이 정상 동작하려면 `localStorage.setItem("accessToken", access)` 를 명시적으로 호출하는 보강이 권장**.

### 7.4 ApiClient (Axios) — `api/ApiClient.ts`

```ts
const API_BASE_URL = import.meta.env.VITE_API_URL || "http://localhost:8080/api/v1"

const apiClient = axios.create({
  baseURL: API_BASE_URL,
  headers: { "Content-Type": "application/json" },
})

// Request: localStorage.accessToken → Bearer 헤더 자동 주입
apiClient.interceptors.request.use((config) => {
  const token = localStorage.getItem("accessToken")
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

const AUTH_ENDPOINTS = ["/auth/login", "/auth/register", "/auth/refresh"]

// Response: 401 자동 재발급 (단, AUTH_ENDPOINTS는 제외하여 로그인 실패 메시지 보존)
apiClient.interceptors.response.use(
  (res) => res,
  async (error) => {
    const original = error.config
    const isAuthEndpoint = AUTH_ENDPOINTS.some((p) => original?.url?.includes(p))
    if (error.response?.status === 401 && !original._retry && !isAuthEndpoint) {
      original._retry = true
      try {
        const refreshToken = localStorage.getItem("refreshToken")
        if (!refreshToken) throw new Error("no refresh token")
        const { data } = await axios.post(`${API_BASE_URL}/auth/refresh`, { refreshToken })
        localStorage.setItem("accessToken", data.accessToken)
        localStorage.setItem("refreshToken", data.refreshToken)
        original.headers.Authorization = `Bearer ${data.accessToken}`
        return apiClient(original)
      } catch {
        localStorage.clear()
        window.location.href = "/login"
      }
    }
    return Promise.reject(error)
  },
)
```

> **주의**: `/auth/refresh` 요청 본문이 `{ refreshToken }` 형태로 전송되지만, 서버는 `Authorization: Bearer <refresh>` 헤더에서 토큰을 추출한다(`JwtRefreshGuard`). 본문은 무시된다. 새 구현 시 서버 동작에 맞추려면 클라이언트도 `axios.post(.../auth/refresh, null, { headers: { Authorization: 'Bearer ' + refreshToken } })` 로 호출하는 편이 정확하다. **재현 시 동작이 깨지면 이 부분을 점검**.

## 8. 핵심 동작 시퀀스

### 8.1 로그인 → 인증된 API 호출
```
1. Login.tsx → POST /auth/login {email, password}
2. 응답: { accessToken, refreshToken }
3. setAuth(null, access, refresh)
   - Zustand: { user: null, accessToken, isAuthenticated: true }
   - localStorage["refreshToken"] = refresh
   - apiClient.defaults.headers.common.Authorization = `Bearer ${access}`
4. localStorage["accessToken"] = access  ← 인터셉터가 사용 (Login.tsx에 명시적 추가 필요)
5. GET /user/me → setUser(profile)
6. navigate("/")
```

### 8.2 401 → 자동 재발급
```
1. 임의 API 401 응답
2. Response 인터셉터: AUTH_ENDPOINTS 가 아니면 _retry 마킹
3. POST /auth/refresh body { refreshToken }
   ※ 서버는 Authorization: Bearer 헤더의 토큰만 본다 — 본문 무시
4. 새 토큰 → localStorage 두 키 모두 갱신 → original 재시도
5. 재발급도 실패 → localStorage.clear() → /login
```

### 8.3 이어보기 & 자동 완료
```
1. VideoDetail mount → getProgress(id) → progress.watchedDuration > 0 이면 initialPosition 저장
2. YouTube IFrame 생성 시 playerVars.start = initialPosition
3. 1s 인터벌: getCurrentTime() → currentTime state (버튼 라벨 표시용)
4. 30s 인터벌: updateProgress(id, floor(time), time/duration >= 0.9)
5. 사용자가 "이 영상 수강 완료" 클릭 → updateProgress(id, currentTime, true) → isCompleted=true 마킹
```

### 8.4 코스 → 영상 등록 (TEACHER 흐름)
```
1. /courses/create → POST /teacher  → { id }
2. /videos/register/:id 자동 이동
3. YouTube ID + 제목 + 초 입력 → POST /videos
4. 반복 등록 → "완료" → /courses/:id 에서 영상 목록 확인
```

### 8.5 수강 신청 → 영상 시청
```
1. /courses/:id 에서 "수강 신청하기" → POST /courses/:id/enroll → 201 또는 409
2. /videos/:videoId 진입 → GET /videos/:videoId
   - enrollment 없으면 → 403 "수강 신청 후 이용 가능합니다."
3. 정상이면 GET /videos/:videoId/progress → 이어보기 위치 적용
```

## 10. 예외처리 동작 카탈로그

> 모든 에러 응답은 `{ statusCode, message, data: null }`. ValidationPipe 메시지 배열인 경우 첫 번째 요소만 사용. catch되지 않은 예외는 500 / `서버 내부 오류가 발생했습니다.`

| HTTP | 경우 | 메시지 |
| --- | --- | --- |
| 400 | DTO 검증 실패 | DTO 데코레이터의 `message:` (예: `유효한 이메일 형식을 입력해주세요.`, `비밀번호는 영문자와 숫자를 모두 포함해야 합니다.`) |
| 400 | 장바구니에 이미 수강 중 코스 추가 | `이미 수강 중인 강좌입니다.` |
| 401 | 로그인 실패 | `이메일 또는 비밀번호가 올바르지 않습니다.` |
| 401 | Access 토큰 만료/없음 | Nest passport 기본 `Unauthorized` (인터셉터가 재발급 시도) |
| 401 | Refresh 검증 실패 | `리프레시 토큰이 아닙니다.` / `리프레시 토큰이 없습니다.` / `유효하지 않은 리프레시 토큰입니다.` |
| 403 | 수강 안한 영상 진입 | `수강 신청 후 이용 가능합니다.` |
| 403 | 비강사가 코스/영상 등록 | `수강 등록은 선생님만 할 수 있습니다.` / `강사만 영상을 등록할 수 있습니다.` |
| 403 | 다른 강사 코스에 영상 등록 | `본인의 코스에만 영상을 등록할 수 있습니다.` |
| 403 | 1편도 안 본 채 리뷰 작성 | `영상 1개 이상을 수강 완료한 후 리뷰를 작성할 수 있습니다.` |
| 403 | 타인 리뷰/북마크 수정·삭제 | `본인의 리뷰만 수정/삭제할 수 있습니다.` / `본인의 북마크만 수정/삭제할 수 있습니다.` |
| 404 | 리소스 미존재 | `존재하지 않는 사용자입니다.` / `존재하지 않는 강좌입니다.` / `영상을 찾을 수 없습니다.` / `리뷰를 찾을 수 없습니다.` / `북마크를 찾을 수 없습니다.` / `강의를 찾을 수 없습니다.` |
| 409 | 이메일 중복 | `이미 사용 중인 이메일입니다.` |
| 409 | 중복 수강 신청 | `이미 수강 신청된 강좌입니다.` |
| 409 | 중복 장바구니 | `이미 장바구니에 담긴 강좌입니다.` |
| 409 | 중복 리뷰 | `이미 리뷰를 작성하셨습니다.` |
| 500 | 알 수 없는 오류 | `서버 내부 오류가 발생했습니다.` (AllExceptionFilter) |
| 500 | 수강/코스 생성 결과 null | `서버 오류: 수강 신청이 완료되지 않았습니다.` / `서버 오류: 강의 등록에 실패하였습니다.` |

## 11. 종단 검증 시나리오 (재현 확인용)

1. **회원가입/로그인**: `student@test.com / abcd1234` (학생), `teacher@test.com / abcd1234` (강사). Swagger `/api/docs` 에서 `POST /auth/login` → 토큰 발급 → "Authorize" 버튼으로 access-token 입력 → 다른 API 호출 가능.
2. **TEACHER 흐름**: `/courses/create` → 한식·LOW·`["knife","pan"]`·무료 → 자동으로 `/videos/register/:id` → YouTube ID `eU6VoHNUT1M`, 제목 "테스트 영상", duration 120 → 등록 → "완료" → 코스 상세에서 영상 1개 보임.
3. **STUDENT 흐름**: 강사가 만든 코스 상세에서 "수강 신청하기" → 성공 → `/my-courses` 에 표시. 영상 클릭 → YouTube 임베드 재생.
4. **이어보기**: 영상 30초 이상 재생 후 다른 페이지로 이동 → 다시 들어오면 그 위치부터 시작.
5. **완료 처리**: "이 영상 수강 완료" 버튼 클릭 → 버튼이 비활성화되며 ✅ 표기.
6. **리뷰**: 영상 1개 완료 후 코스 상세에서 별점·내용 입력 → 등록. 다시 같은 코스에 작성 시 409. 본인 리뷰만 수정/삭제 가능.
7. **북마크**: 영상 임의 시점에 메모 "비율 중요" 입력 → 북마크 → 사이드패널에 표시 → 삭제 가능.
8. **장바구니**: TEACHER가 유료 코스(예: 10000원) 생성 → STUDENT가 "🛒 장바구니 담기" → `/cart` 에서 확인 → "결제하기" 클릭 → 일괄 enrollment + cart 비움 → "🎉 결제 완료" → "내 강의 보기" 진입 가능.
9. **다국어 검증 에러**: 회원가입 시 비밀번호 `pass` 입력 → 400 + `비밀번호는 최소 8자 이상이어야 합니다.` 메시지.
10. **권한 분리**: 비로그인 상태에서 `/my-courses` 접근 → `/login` 으로 리다이렉트. STUDENT가 `/teacher` 접근 → `/` 로 리다이렉트.

이 10개 시나리오가 동일한 결과를 내면 P2와 동등한 구현이라 간주한다.

## 12. 알려진 차이/주의사항 정리

| 항목 | 원본 P2 동작 | 권장 보강 (선택) |
| --- | --- | --- |
| `client/index.html`이 `/src/main.jsx` 참조 (실제는 `.tsx`) | Vite가 어떻게든 해석 | `main.tsx`로 수정 |
| `Login.tsx`가 `localStorage["accessToken"]` 직접 저장 X | `apiClient.defaults`에만 토큰 세팅. 새로고침 시 인터셉터가 못 읽음 | `setAuth` 호출 직후 `localStorage.setItem("accessToken", access)` 추가 |
| `/auth/refresh` 호출 시 본문에 `{refreshToken}` 전송, 헤더엔 access token | 서버는 헤더에서 refresh 추출 → 본문 무시 → 401 발생 가능 | 클라이언트가 `axios.post(.../auth/refresh, null, { headers: { Authorization: 'Bearer ' + refreshToken }})` 로 보내도록 수정 |
| 리뷰 작성 조건이 명세서엔 80% / 코드엔 "1편 이상" | 코드 따름 — 1편 완료면 작성 가능 | 정책 결정 후 일치시킴 |
| `course.category`가 영어 enum / `CourseCard`는 한글 키 매핑 사용 → 이모지가 폴백 🍽️ 로 표시됨 | 그대로 — 의도된 상태가 아닐 가능성 | CourseCard에 영어→한글 라벨 변환 추가 |
| CORS `origin: true` | 개발 편의 — 프로덕션에선 도메인 화이트리스트로 변경 |  |
| Helmet / Throttler / Rate-limit | 미적용 | 프로덕션 도입 권장 (로그인 15분/20회 등) |
| `synchronize: true` (dev) | DB 스키마 자동 동기화 — 개발 OK | 프로덕션은 migrations 사용 |
| 토스페이먼츠 연동 | 미구현 — 장바구니 결제는 enroll 일괄 호출로 대체 |  |
